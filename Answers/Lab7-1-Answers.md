## 1. ผลการทดลอง (Results)

### 1.1 Boot Log ที่ได้จากบอร์ดจริง

```
rst:0x1 (POWERON_RESET),boot:0x13 (SPI_FAST_FLASH_BOOT)
I (27) boot: ESP-IDF v6.0.2 2nd stage bootloader
I (29) boot: chip revision: v3.1
I (39) boot.esp32: SPI Flash Size : 2MB
I (399) boot: Loaded app from partition at offset 0x10000
I (424) app_init: Project name:     lab7_1_reset_nvs_forensics
I (443) app_init: ESP-IDF:          v6.0.2
I (512) LAB7_1_RESET: Hold GPIO 18 button for 3 seconds to trigger Factory Reset...
W (612) LAB7_1_RESET: [STATUS]: Device is NOT provisioned (NVS is empty)
W (622) LAB7_1_RESET: Ready for Provisioning Lab 7-2 (SoftAP) or 7-3 (BLE)!
```

**จุดสังเกตสำคัญจาก Log**

| บรรทัด | ความหมาย |
| :--- | :--- |
| `rst:0x1 (POWERON_RESET)` | สาเหตุการรีเซ็ตคือการจ่ายไฟใหม่ ไม่ใช่ Watchdog หรือ Panic |
| `boot:0x13 (SPI_FAST_FLASH_BOOT)` | ค่า Strapping ที่ถูก latch ตอนรีเซ็ต บอกว่า **GPIO 0 = HIGH** ชิปจึงบูตจาก SPI Flash ตามปกติ |
| `Loaded app from partition at offset 0x10000` | โหลด Application จาก partition `factory` สำเร็จ |
| `Device is NOT provisioned (NVS is empty)` | `network_prov_mgr_is_wifi_provisioned()` คืนค่า `false` |

### 1.2 Partition Table ที่อ่านได้ตอน Boot

| # | Label | Usage | Type | ST | Offset | Length | ขอบเขตที่กินพื้นที่ |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 0 | `nvs` | WiFi data | 01 | 02 | `0x009000` | `0x006000` (24 KB) | `0x009000`–`0x00EFFF` |
| 1 | `phy_init` | RF data | 01 | 01 | `0x00F000` | `0x001000` (4 KB) | `0x00F000`–`0x00FFFF` |
| 2 | `factory` | factory app | 00 | 00 | `0x010000` | `0x100000` (1 MB) | `0x010000`–`0x10FFFF` |

> ตารางนี้คือหลักฐานสำคัญที่ใช้ตอบคำถามข้อ 2 — พื้นที่ `nvs` กับ `factory` **แยกขาดจากกัน ไม่ทับซ้อนกันเลย**

### 1.3 ตารางบันทึกผลการทดลอง Reset ทั้ง 3 รูปแบบ

| รูปแบบการ Reset | คำสั่ง / พฤติกรรม | ขอบเขตที่ถูกลบ | สถานะใน Serial Monitor | เฟิร์มแวร์หาย |
| :--- | :--- | :--- | :--- | :--- |
| **1. CLI Erase** | `idf.py -p COM3 erase-flash` | **ทั้งชิป** ตั้งแต่ `0x000000` | หลังลบต้อง flash ใหม่ ไม่งั้นบอร์ดบูตไม่ขึ้น | **หาย** |
| **2. Menuconfig Flag** | `CONFIG_EXAMPLE_RESET_PROVISIONED=y` | เฉพาะ key Wi-Fi ใน namespace `nvs.net80211` | `Device is NOT provisioned` ทุกครั้งที่บูต | ไม่หาย |
| **3. Hardware Button** | กด GPIO 18 ค้าง 3 วินาที | เฉพาะ partition `nvs` (`0x009000`–`0x00EFFF`) | `>>> FACTORY RESET TRIGGERED! ERASING NVS FLASH <<<` | ไม่หาย |

**สถานะ LED 1 (GPIO 2) ที่สังเกตได้จริง:** ดับสนิท เนื่องจาก `g_led_mode` ยังเป็น `LED_STA_OFF`
และยังไม่มีการเรียก `esp_wifi_start()` เพราะอุปกรณ์ยังไม่ถูก provision จึงยังไม่เกิด event
`WIFI_EVENT_STA_START` ที่จะเปลี่ยนโหมดไฟเป็น `LED_STA_DISCONNECTED`

## 2. คำถามท้ายการทดลอง (Post-Lab Questions)

### ข้อ 1. เพราะเหตุใดการกดปุ่ม BOOT (GPIO 0) ค้างไว้ในจังหวะรีเซ็ตบอร์ด จึงทำให้โปรแกรมค้างอยู่ที่ ROM Bootloader และไม่ยอมทำงานต่อ

เพราะ **GPIO 0 เป็น Strapping Pin** ที่ชิปใช้เลือกโหมดการบูต โดยมีกลไกดังนี้

**1) จังหวะการอ่านค่าเกิดขึ้นครั้งเดียวและสั้นมาก**

ในจังหวะที่สัญญาณ Reset ถูกปลด ชิปจะ **latch หรือล็อกค่า** ระดับลอจิกของ Strapping Pins
เข้าเก็บไว้ในรีจิสเตอร์ `GPIO_STRAP` เพียงครั้งเดียว หลังจากนั้น GPIO 0 จะกลับไปเป็นขา I/O ธรรมดาทันที

**2) ค่าที่ latch ได้เป็นตัวกำหนดเส้นทางการบูต**

| GPIO 0 ตอน Reset | โหมดที่เลือก | ผลลัพธ์ |
| :--- | :--- | :--- |
| `HIGH (1)` ปกติ มี pull-up ภายใน | **SPI Flash Boot** | อ่าน 2nd stage bootloader ที่ `0x1000` แล้วโหลด app และเรียก `app_main()` |
| `LOW (0)` กดปุ่ม BOOT ค้าง | **UART Download Boot** | ค้างรอ esptool ทาง UART แสดงข้อความ `waiting for download` |

**3) เหตุที่ไม่ยอมทำงานต่อ**

ในโหมด Download นั้น **ROM Bootloader ซึ่งเป็นโค้ดใน Mask ROM ที่ลบไม่ได้ จะไม่แตะ SPI Flash เลย**
มันเข้าสู่ลูปรอรับคำสั่งผ่าน UART อย่างเดียว จึง **ไม่มีการโหลด 2nd stage bootloader และไม่มีการโหลด Application**
ผลคือ `app_main()` ไม่เคยถูกเรียก

จุดนี้เป็นความเข้าใจผิดที่พบบ่อย — ไม่ใช่ว่าโปรแกรมของเรา "ค้าง" หรือ "แฮงก์"
แต่คือ **โปรแกรมไม่เคยถูกโหลดขึ้นมาตั้งแต่แรก** ต่างหาก

**4) หลักฐานยืนยันจาก Log ของการทดลองนี้**

```
rst:0x1 (POWERON_RESET),boot:0x13 (SPI_FAST_FLASH_BOOT)
```

ค่า `boot:0x13` คือค่า Strapping ที่ latch ได้ ซึ่งชี้ว่า GPIO 0 เป็น HIGH ชิปจึงเลือก `SPI_FAST_FLASH_BOOT`
หากกดปุ่ม BOOT ค้างไว้ ค่านี้จะเปลี่ยนเป็นโหมด `DOWNLOAD_BOOT` แทน และจะไม่มีบรรทัด
`I (27) boot: ESP-IDF v6.0.2 2nd stage bootloader` ตามมาเลย

> **ข้อควรระวัง** เนื่องจากค่าถูก latch เฉพาะตอนรีเซ็ต การปล่อยปุ่มทีหลังจึงไม่ช่วยให้หลุดจากโหมด Download
> ต้องกดรีเซ็ตใหม่โดยที่ GPIO 0 เป็น HIGH เท่านั้น
> นี่คือเหตุผลที่ใบงานนี้เลือกใช้ **GPIO 18** ซึ่งเป็นขา I/O ธรรมดาที่ไม่ใช่ Strapping Pin มาทำปุ่ม Factory Reset แทน

### ข้อ 2. เพราะเหตุใดคำสั่ง `idf.py erase-flash` จึงทำให้ข้อมูลเฟิร์มแวร์ Application หายไปด้วย ในขณะที่ `nvs_flash_erase()` ไม่ทำให้เฟิร์มแวร์หาย

คำตอบหลักคือ ทั้งสองคำสั่งทำงานคนละชั้นนามธรรม และ **รู้จัก Partition Table ไม่เท่ากัน**

#### เปรียบเทียบเชิงโครงสร้าง

| ประเด็น | `idf.py erase-flash` | `nvs_flash_erase()` |
| :--- | :--- | :--- |
| ผู้สั่งงาน | esptool บน **พีซี** | โค้ดที่รันอยู่บน **ESP32** |
| ช่องทาง | UART ผ่าน ROM Download Bootloader | เรียก NVS driver ในเฟิร์มแวร์โดยตรง |
| ระดับการทำงาน | **Raw Flash / Chip Erase** | **Partition-aware** |
| รู้จัก Partition Table | **ไม่รู้จัก** | **รู้จัก** |
| ขอบเขตที่ลบ | ทั้งชิปตั้งแต่ `0x000000` | เฉพาะ `0x009000`–`0x00EFFF` |

#### 1) `idf.py erase-flash` ลบแบบไม่เลือกหน้า

คำสั่งนี้เรียก `esptool erase_flash` ซึ่งส่ง **Chip Erase command** ไปยังชิป SPI Flash โดยตรง
ในมุมมองของ esptool ตัว Flash เป็นเพียง **อาร์เรย์ของไบต์ก้อนเดียว** ไม่มีแนวคิดเรื่อง partition ใด ๆ ทั้งสิ้น
ดังนั้นทุกอย่างจึงถูกลบเรียบ ได้แก่

- `0x001000` — 2nd stage bootloader
- `0x008000` — **Partition Table เอง**
- `0x009000` — NVS
- `0x010000` — **Application หรือ factory** ตรงนี้เองที่เฟิร์มแวร์อยู่ จึงหายไปด้วย

ผลคือหลัง `erase-flash` บอร์ดจะบูตไม่ขึ้น ต้อง `idf.py flash` ใหม่ทั้งชุด

#### 2) `nvs_flash_erase()` ลบแบบเลือกเฉพาะจุด

ฟังก์ชันนี้รันอยู่ **ภายในเฟิร์มแวร์ที่กำลังทำงานอยู่** ขั้นตอนคือ

1. เปิด Partition Table ที่ `0x8000` เพื่อค้นหา partition ที่มี `type=data, subtype=nvs`
2. จากตารางในหัวข้อ 1.2 ได้ผลลัพธ์คือ offset `0x009000` ยาว `0x006000`
3. สั่ง erase **เฉพาะ sector ในช่วงนั้น** เท่านั้น

เนื่องจาก partition `factory` เริ่มที่ `0x010000` ซึ่ง **อยู่นอกช่วง `0x009000`–`0x00EFFF` อย่างสิ้นเชิง**
โค้ด Application จึงปลอดภัย ไม่ถูกแตะต้อง

#### 3) ข้อสังเกตเชิงตรรกะที่สำคัญ

`nvs_flash_erase()` **ไม่มีทางลบเฟิร์มแวร์ตัวเองได้** เพราะถ้ามันลบพื้นที่ `factory` ทิ้ง
ก็เท่ากับลบโค้ดที่ตัวเองกำลังรันอยู่ ซึ่งจะทำให้ระบบพังกลางคันทันที
การออกแบบให้ทำงานแบบ partition-aware จึงเป็นทั้งเรื่องความถูกต้องและความปลอดภัย

### ข้อ 3. การออกแบบปุ่ม Factory Reset บนอุปกรณ์ IoT เชิงพาณิชย์ เหตุใดจึงต้องกำหนดให้ผู้ใช้กดปุ่มค้างไว้ 3-5 วินาที แทนที่จะสั่งลบข้อมูลทันทีที่แตะปุ่มเพียงเสี้ยววินาที

เหตุผลแบ่งได้เป็น 4 มิติ

#### 1) ป้องกันการลบโดยไม่ตั้งใจ เป็นเหตุผลหลัก

Factory Reset เป็นการกระทำที่ **ทำลายข้อมูลและย้อนกลับไม่ได้**
ผู้ใช้ต้องตั้งค่า Wi-Fi ใหม่ทั้งหมด หากลบทันทีที่แตะ อุบัติเหตุต่อไปนี้จะเกิดขึ้นได้ง่ายมาก

- เด็กเล็กหรือสัตว์เลี้ยงกดเล่น
- ปุ่มถูกกดโดนระหว่างขนส่ง ติดตั้ง หรือทำความสะอาด
- ผู้ใช้กดผิดปุ่ม เพราะอุปกรณ์ headless มักมีปุ่มเดียวหลายหน้าที่

#### 2) ทำหน้าที่เป็นกล่องยืนยันของอุปกรณ์ที่ไม่มีจอ

บนคอมพิวเตอร์ การลบข้อมูลสำคัญจะมี Dialog ถามยืนยัน แต่อุปกรณ์ IoT เป็น **Headless Device**
ไม่มีจอให้กด OK หรือ Cancel ดังนั้น **ระยะเวลาที่กดค้างจึงถูกใช้แทน Confirmation Dialog**
เป็นการพิสูจน์ว่าผู้ใช้ตั้งใจจริง ไม่ใช่การกดโดนโดยบังเอิญ

#### 3) กรองสัญญาณรบกวนทางไฟฟ้า

- **Contact Bounce** สวิตช์กลไกจะเกิดการกระเด้ง สร้างพัลส์ HIGH/LOW หลายสิบครั้งในช่วงไม่กี่มิลลิวินาที
- **EMI และ ESD** สายที่ต่อยาวอาจรับสัญญาณรบกวนจนขาถูกดึงลง LOW ชั่วขณะ

การบังคับให้สถานะ LOW **ต่อเนื่องยาวนานถึง 3 วินาที** ทำให้สัญญาณรบกวนระดับไมโครวินาที
ไม่มีทางกระตุ้นการลบข้อมูลได้เลย ซึ่งในโค้ดของเราทำผ่านลูปนี้

```c
while (gpio_get_level(FACTORY_RESET_BUTTON_GPIO) == 0) {
    vTaskDelay(pdMS_TO_TICKS(100));
    hold_count++;
    if (hold_count >= 30) {   // ต้องครบ 30 x 100ms = 3 วินาที
        return true;
    }
}
return false;   // ปล่อยปุ่มก่อนครบ เท่ากับยกเลิกทันที
```

สังเกตว่าถ้าผู้ใช้ปล่อยปุ่มก่อนครบ 3 วินาที ลูปจะหลุดออกและ `return false` ทันที
เท่ากับ **ผู้ใช้สามารถยกเลิกได้ตลอดเวลาโดยแค่ปล่อยมือ**

#### 4) เปิดโอกาสให้แจ้ง Feedback และให้ผู้ใช้ยกเลิกได้ทัน

ช่วง 3 วินาทีนี้เปิดพื้นที่ให้เฟิร์มแวร์ส่งสัญญาณเตือน เช่น ไฟกระพริบถี่ขึ้นเรื่อย ๆ หรือเสียง Beep
เพื่อบอกว่ากำลังจะรีเซ็ตแล้ว ในโค้ดของเราใช้ Log แจ้งนับถอยหลัง

```c
if (hold_count % 10 == 0) {
    ESP_LOGI(TAG, "Holding button... %d/3 seconds", hold_count / 10);
}
```

**ผลพลอยได้** การใช้ระยะเวลาแยกแยะยังทำให้ **ปุ่มเดียวทำได้หลายหน้าที่** เช่น
กดสั้นคือเปิดปิด กดค้าง 3 วินาทีคือ Factory Reset ซึ่งช่วยลดจำนวนปุ่มและต้นทุนการผลิต

### ข้อ 4. หากอุปกรณ์ IoT ถูกติดตั้งอยู่บนเสาสูงหรือฝังอยู่ในผนัง วิธีการ Reset ทางกายภาพรูปแบบใดเหมาะสมที่สุด

**คำตอบ ใช้วิธี Power-Cycle Pattern Reset หรือการกระพริบสวิตช์ไฟตามจังหวะที่กำหนด**

#### หลักการทำงาน

ผู้ใช้เปิดและปิดสวิตช์ไฟหลักที่จ่ายให้อุปกรณ์ **ติดต่อกันหลายครั้งภายในเวลาที่กำหนด**
เช่น เปิดปิด 5 ครั้ง โดยแต่ละครั้งเว้นไม่เกิน 2 วินาที เฟิร์มแวร์จะนับจำนวนครั้งแล้วสั่ง Factory Reset

**กลไกการนับ** ทำได้ 2 แบบ

1. **RTC Memory** ตัวแปรที่ประกาศด้วย `RTC_NOINIT_ATTR` จะคงค่าข้ามการรีเซ็ตแบบ soft ได้
2. **NVS Counter** เขียนตัวนับลง NVS ตอนบูต แล้วตั้ง Timer ไว้ ถ้าอุปกรณ์อยู่รอดเกิน N วินาที ให้ล้างตัวนับกลับเป็นศูนย์

ตรรกะคือ ถ้าบูตแล้วอยู่ได้ไม่นานก็ถูกตัดไฟอีก แสดงว่าผู้ใช้กำลังตั้งใจกระพริบสวิตช์

| วิธี | ข้อดี | ข้อจำกัด |
| :--- | :--- | :--- |
| **Magnetic Reed Switch** | ใช้แม่เหล็กแตะผ่านผนังหรือเคสได้ ไม่ต้องเจาะรู | ต้องพกแม่เหล็ก และยังต้องเข้าใกล้ตัวอุปกรณ์ |
| **BLE Reset พร้อม PoP** | สั่งจากมือถือได้ ปลอดภัยเพราะมี PoP ยืนยัน | ใช้ไม่ได้ถ้าเฟิร์มแวร์ค้างหรือ BLE stack พัง |
| **OTA หรือ Cloud Reset** | สั่งจากที่ไหนก็ได้ | **ใช้ไม่ได้เลยในกรณีที่ต้อง reset บ่อยที่สุด** คือตอนที่อุปกรณ์ต่อเน็ตไม่ได้ |
| **ปุ่มกดทางกายภาพ** | ทำงานได้เสมอ | **ขัดกับโจทย์โดยตรง** เพราะเข้าถึงตัวอุปกรณ์ไม่ได้ |

#### สรุปเชิงออกแบบ

ควรออกแบบให้มี **หลายชั้นซ้อนกันหรือ Layered Fallback** เพื่อความทนทาน

1. **ชั้นปกติ** สั่ง Reset ผ่านแอปด้วย BLE หรือ Cloud สะดวกที่สุด
2. **ชั้นสำรอง** Power-Cycle Pattern ใช้ได้แม้เน็ตล่มหรือแอปใช้ไม่ได้
3. **ชั้นสุดท้าย** ปุ่มกดจริงซ่อนไว้ในตัวเครื่อง สำหรับช่างเท่านั้น

โดย **Power-Cycle Pattern คือชั้นที่ตอบโจทย์เสาสูงและฝังผนังได้ตรงที่สุด**
เพราะทำงานได้แม้อุปกรณ์ต่อเน็ตไม่ได้ และไม่ต้องเข้าถึงตัวเครื่องเลย

## 3. สรุปผลการทดลอง (Conclusion)

1. **กลไก Reset ทั้ง 3 รูปแบบทำงานคนละระดับชั้น และมีขอบเขตการทำลายข้อมูลต่างกันชัดเจน**
   `erase-flash` ทำงานระดับ raw flash จากภายนอกจึงลบทั้งชิปรวมถึงเฟิร์มแวร์
   ส่วน `nvs_flash_erase()` ทำงานระดับ partition จากภายในจึงลบเฉพาะ NVS ขนาด 24 KB
   ที่ offset `0x009000` เท่านั้น

2. **Strapping Pin เป็นข้อจำกัดทางฮาร์ดแวร์ที่ต้องออกแบบหลบ**
   GPIO 0 ถูก latch ค่าตอนรีเซ็ตเพื่อเลือกโหมดบูต การนำมาทำปุ่ม Factory Reset
   จะทำให้บอร์ดตกไปอยู่ในโหมด Download แทน ใบงานจึงใช้ GPIO 18 ซึ่งเป็น I/O ธรรมดา

3. **การกดค้าง 3 วินาทีไม่ใช่แค่การหน่วงเวลา แต่คือกลไกยืนยันเจตนาของอุปกรณ์ headless**
   ทำหน้าที่แทน Confirmation Dialog พร้อมกันกับกรองสัญญาณรบกวนและเปิดโอกาสให้ยกเลิกได้

4. **ยืนยันการทำงานบนฮาร์ดแวร์จริงด้วย ESP-IDF v6.0.2 สำเร็จ**
   บอร์ดบูตด้วย `SPI_FAST_FLASH_BOOT` โหลด app จาก `0x010000` และ
   `network_prov_mgr_is_wifi_provisioned()` รายงานสถานะ `NOT provisioned` ได้ถูกต้อง

### ข้อสังเกตเพิ่มเติมที่พบระหว่างการทดลอง

พบ Warning จาก Log ว่า

```
W (498) spi_flash: Detected size(4096k) larger than the size in the binary image header(2048k).
```

หมายความว่า **บอร์ดจริงมี Flash 4 MB แต่ค่าคอนฟิกตั้งไว้เพียง 2 MB**
ระบบยังทำงานได้ปกติเพราะ partition ทั้งหมดรวมกันไม่เกิน 2 MB
แต่เท่ากับว่ามีพื้นที่ Flash ราวครึ่งหนึ่งที่ไม่ได้ถูกนำมาใช้ประโยชน์
หากต้องการใช้เต็มความจุ สามารถแก้ที่ `sdkconfig.defaults` เป็น
`CONFIG_ESPTOOLPY_FLASHSIZE_4MB=y`
