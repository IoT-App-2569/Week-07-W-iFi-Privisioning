## 6. กิจกรรมถอดรหัสซอร์สโค้ดและเขียนผังงาน (Code Deconstruction & Security Flow Assignment)

ให้นักศึกษาแกะรอยการทำงานด้านความปลอดภัยและ Custom Handler ใน `main/main.c` แล้วเขียน **ผังการไหลของข้อมูล (Data Flow & Cryptographic Handshake Flow)**:

### ภารกิจที่ 1: ผังขั้นตอนการตรวจสอบ PoP (Security Handshake Decision Flow)
ให้นักศึกษาวาด Flowchart แสดงการแลกเปลี่ยนคีย์และตรวจสอบสิทธิ์:
1. การสร้าง Session Parameters ด้วยค่า PoP (`abcd1234`)
2. เมื่อ Client ส่ง Public Key + Verification Hash มาให้ ESP32
3. จุดแยกทางเลือก (Branching):
   - หาก PoP ไม่ตรง $\rightarrow$ Trigger Event `PROTOCOMM_SECURITY_SESSION_CREDENTIALS_MISMATCH` และปฏิเสธการเชื่อมต่อ
   - หาก PoP ถูกต้อง $\rightarrow$ Trigger Event `PROTOCOMM_SECURITY_SESSION_SETUP_OK` และสร้าง AES Session Key สำเร็จ

### ภารกิจที่ 2: ผังการรับส่งข้อมูลผ่าน Custom Endpoint (Custom Data Handler Flow)
ให้นักศึกษาวาด Sequence / Data Flow ของฟังก์ชัน `custom_prov_data_handler()`:
1. ข้อมูล `inbuf` ถูกส่งเข้ามาจากสมาร์ตโฟนผ่าน Protocomm
2. การพิมพ์ข้อความ Log ด้วย `ESP_LOGI()`
3. การจัดสรรหน่วยความจำแบบไดนามิกด้วย `strdup()` ให้กับ `*outbuf`
4. ทำไมตัวแปร `*outbuf` จึงต้องจัดสรรใน Heap Memory (ทำไมจึงใช้ตัวแปร Local Static Array ธรรมดาไม่ได้)?

## 8. คำถามท้ายการทดลอง (Post-Lab Questions)
1. การใช้ **Proof-of-Possession (PoP)** ช่วยป้องกันการโจมตีประเภทใดได้บ้าง?
> Man-in-the-Middle (MitM) Attack: ป้องกันผู้โจมตีที่แอบแทรกตัวอยู่ระหว่างมือถือกับ ESP32 ในขั้นตอนการแลกเปลี่ยนคีย์ (Diffie-Hellman Key Exchange) เนื่องจาก PoP จะถูกนำไปใช้พิสูจน์สิทธิ์และสร้าง Session Key หากไม่มี PoP ที่ถูกต้อง ผู้โจมตีจะไม่สามารถปลอมแปลงตัวตนหรือถอดรหัสการสื่อสารได้ Unauthorized Provisioning (การเข้าควบคุมอุปกรณ์โดยไม่ได้รับอนุญาต): ป้องกันบุคคลอื่นในรัศมีสัญญาณบลูทูธไม่ให้สามารถเชื่อมต่อเข้ามาส่งค่าการตั้งค่า Wi-Fi หรือควบคุมอุปกรณ์ได้ เว้นแต่ผู้ใช้นั้นจะมี PoP ที่ติดอยู่บนตัวอุปกรณ์จริง (เช่น สแกนจาก QR Code หรือรหัสข้างกล่อง)
2. หากไม่มีการใช้ PoP (เช่น ใน Security 0) ผู้โจมตีที่อยู่ในรัศมีสัญญาณบลูทูธสามารถทำสิ่งใดกับอุปกรณ์ได้บ้าง?
> ดักจับรหัสผ่าน Wi-Fi (Credential Sniffing): ข้อมูล SSID และ Password ของ Wi-Fi จะถูกส่งผ่านบลูทูธแบบ Plaintext (ไม่มีการเข้ารหัส) ผู้โจมตีในรัศมีสัญญาณสามารถใช้ Bluetooth Sniffer ดักรับข้อมูลเพื่อนำรหัสผ่าน Wi-Fi ไปใช้งานได้ทันที สวมรอยเชื่อมต่อ (Rogue Provisioning): ผู้โจมตีสามารถส่ง SSID และ Password ของ Wi-Fi ปลอม (Rogue AP) เข้าไปที่ ESP32 เพื่อบังคับให้อุปกรณ์ไปเชื่อมต่อกับเครือข่ายของผู้โจมตีเพื่อทำโจมตีต่อยอด ก่อกวนระบบ (Denial of Service - DoS): ผู้โจมตีสามารถส่งค่าการตั้งค่า Wi-Fi ที่ผิดพลาดเข้าไปยังอุปกรณ์ได้ตลอดเวลา ทำให้อุปกรณ์ไม่สามารถเชื่อมต่ออินเทอร์เน็ตเพื่อทำงานตามปกติได้
3. ในการประยุกต์ใช้งานเชิงพาณิชย์จริง เราสามารถนำ **Custom Data Endpoint** ไปใช้ส่งข้อมูลประเภทใดได้อีกบ้าง (ยกตัวอย่าง 2 กรณี)?
> **กรณีที่ 1**: การส่ง User Auth Token / Device Binding Key: ใช้ส่งรหัสยืนยันตัวตนของผู้ใช้ (เช่น JWT Token หรือ Provisioning Token จาก Cloud) เพื่อทำการผูกอุปกรณ์ (Bind Device) เข้ากับบัญชีผู้ใช้ในระบบคลาวด์ (เช่น AWS IoT, Firebase หรือ Tuya) ทันทีที่ตั้งค่า Wi-Fi สำเร็จ **กรณีที่ 2**: การตั้งค่าเริ่มต้นของอุปกรณ์ (Initial Setup & Metadata): ใช้ส่งข้อมูลประจำตัวและสภาพแวดล้อมของอุปกรณ์ เช่น การกำหนดชื่ออุปกรณ์ ("Smart Light Living Room"), การระบุตำแหน่งห้อง (Room ID), การตั้งค่าเขตเวลา (Timezone / NTP Offset) หรือพารามิเตอร์เริ่มต้นของการทำงาน
4. ในฟังก์ชัน `custom_prov_data_handler()` เหตุใดหน่วยความจำที่จัดสรรให้ `*outbuf` จึงถูก Free โดย Protocomm Layer อัตโนมัติหลังจากส่งข้อมูลเสร็จ?
> การโอนสิทธิ์ดูแลหน่วยความจำ (Ownership Transfer): ในฟังก์ชัน handler ฝั่งแอปพลิเคชันจะทำการจองหน่วยความจำ (เช่น ใช้ malloc() หรือ calloc()) เพื่อสร้างข้อมูลตอบกลับ (Response Data) และส่งมอบ Pointer (*outbuf) ให้กับ Protocomm Layer การทำงานแบบ Asynchronous และการป้องกัน Memory Leak: กระบวนการเข้ารหัสข้อมูล (Encryption) และการส่งแพ็กเกจออกไปทาง Bluetooth LE จะเกิดขึ้นหลังจากฟังก์ชัน handler ทำงานเสร็จสิ้น Protocomm Layer จึงต้องรับหน้าที่ถือ Pointer ไว้จนกว่าจะส่งข้อมูลผ่านฮาร์ดแวร์บลูทูธเรียบร้อย แล้วจึงทำการเรียก free(*outbuf) ทิ้งให้อัตโนมัติ เพื่อป้องกันปัญหาหน่วยความจำรั่วไหล (Memory Leak) และป้องกันไม่ให้เกิดการคืนหน่วยความจำซ้ำซ้อน (Double Free)
